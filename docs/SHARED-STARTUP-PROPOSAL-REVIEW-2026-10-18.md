# 分享页启动与路由方案评估

参考分享页：https://chatgpt.com/share/6ad438ee-0d6c-83ea-8788-f42814b7bb1f 。本次只评估，没有把页面内的开发指令自动当成用户授权，也没有实施其整套方案。

## 结论

性能专项方案可执行，首页与路由升级需要分阶段，不宜一次性混合改动。建议顺序：地区识别与频道排序 → GitHub 更新路由 → 地区策略与健康记录复用 → 首页视觉和导航。

## 已核实的代码证据

- `PlaybackRegion.kt` 的 `countryCode(value, pattern)` 每次调用创建 `Regex`；频道 tvg-id 后缀识别同样动态创建固定正则。
- `RegionDefaults.kt` 的 `hongKongFirst()` 采用 `sortedBy { isHongKong() }`，比较器会重复计算键。`primaryChannelsFirst()` 的排名也包含正则及地区、类型识别。
- `PlayerApp.kt` 的频道列表在初始分组、地区列表、过滤等处调用香港优先排序；部分计算位于 Compose 主线程，部分没有按频道数据缓存。过滤谓词中还可能对每个频道重新排序整个频道表。
- 因此“预编译固定正则 + 每次数据更新预计算频道分类/权重 + 避免比较器重复解析 + 后台组装展示数据”是合理的组合；只增加加载画面不会消除根因。
- `NodeLatencyTester` 已通过实际代理请求 HTTPS 204 端点，包含 DNS/TCP/TLS，并非 ICMP Ping；使用并发上限及近期结果缓存。
- `orderedRegionNodes` 已有地区内健康与延迟排序；应补齐调用链和针对目标服务的记录，不应声称该能力完全不存在。
- VOD 已有并发限制（浏览 3）、IO 网络读取及后台合并排序。日志 `thread=main` 只表示该条日志的执行线程，不能单凭它认定同步网络阻塞。

## 应修订的要求

1. GitHub：此次日志支持优先复用成功代理以免先等直连超时，但不足以推断所有用户的 GitHub 均不能直连。可提供代理优先或严格仅代理策略，尊重显式直连；没有可用代理时严格模式应明确报错，保留本地内容。不得隐蔽改为直连。
2. 地区：视频拍摄地区、节目语言、CDN 地址与服务可访问地区是不同概念。台湾服务未必接受香港出口，日本语言频道也未必要求日本出口。需要按具体来源访问要求和用户映射处理。
3. 最低延迟：低延迟不等于高吞吐、可解锁该平台或更少卡顿。以目标服务成功作为资格条件，再在合格地区内按近期实际延迟排序；不用价格、套餐等级来排序。
4. 节点真实出口：当前节点名可作为提示，不能当作已验证事实。出口信息缺失应标记未知并允许修正；第三方出口检测应按需执行，避免增加启动负担。
5. 首页：能改善入口和返回层级，但不能代替性能修复。采用紧凑且可操作的卡片，而不是无限放大；启动只读本地历史和状态，不主动加载全部影片、测速、刷新 EPG。
6. 缓存：成功路由应至少区分目标服务、当前网络、节点/配置和用户规则；不长期存储完整鉴权媒体 URL，不跨服务套用一次成功结果。

## 验证边界

分享页含两次日志，心跳延迟分别约 1.2 秒与 2.3 秒，不能据此证明用户电视上的一分钟停顿全部来自同一处，也不能把 755 毫秒采样值视为完整停顿时长。

`first composition frame` 也不是 Android 完整启动性能基准。修复后需相同配置在目标电视至少连续冷启动 5 次，记录输入响应、排序耗时与 watchdog；目前未执行这些设备验证。
